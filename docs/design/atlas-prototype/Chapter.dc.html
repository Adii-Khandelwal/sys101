In short

Put servers and keys on the same circle, and let each key belong to the next server around. Add or remove a server and only its neighbours' keys move, instead of nearly everything.

Why modulo breaks

The obvious way to spread keys over N servers is to take the key's hash1 and keep the remainder after dividing by N. It balances well and costs nothing. Then you add one server, N changes, and the remainder changes for almost every key.

A cache fleet that did this would lose most of its contents in one deploy, and every miss would land on the database at the same moment.

1 A function that turns any key into a number. The same key always gives the same number, which is all the ring needs from it.

The ring fixes this by making a key's home depend only on where the servers sit around it, not on how many there are. Turn the dial below: add a server and watch which keys follow it, then compare the count to what modulo would have moved.

Why the bars are uneven

With only a few servers, chance decides how much of the circle each one owns, so some hold twice what others do. The usual cure is to give every machine many places on the ring, called virtual nodes2, so its share averages out.

The same trick lets a bigger machine take more of the circle than a smaller one, simply by giving it more places.

2 One physical server placed on the ring many times under different names. Lose the server and its load scatters across many neighbours instead of landing on one.

What the original system did

Amazon's Dynamo paper used this placement to decide which nodes hold a key, then replicated3 each key onto the next nodes around the ring. Read it for how the authors handled uneven load, and for what they gave up to stay writable.

3 Copied to other machines so the data survives one of them failing. The next chapter after this one picks that thread up.
